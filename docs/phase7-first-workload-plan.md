## 2. Topology, TLS và bootstrap

### 2.1. Một process giữ HTTPS, một app phục vụ UI/API

`tests/m2/e2e/fixture_launcher.py` (Python parent) tạo disposable PostgreSQL manager, certificate qua `loopback_certificate.py`, đúng **một** `BootstrapCapabilityRegistry`, rồi `create_app(manager=..., allowed_origins={"https://localhost:8000"}, bootstrap_registry=registry)`. Cùng launcher mount `src/controlplane/ui/dist` tại `/` **sau** các router `/v1/**`; Uvicorn là process duy nhất bind `127.0.0.1:8000` và giữ TLS socket. Vite chỉ build, không proxy/giữ port runtime. Node 22.17 runner/Playwright 1.50.1 (Chromium 133.0.6943.16) là process con; browser và APIRequestContext dùng `https://localhost:8000`. Đây là test topology, không phải launcher người dùng thật: `src/controlplane/api/tls.py:serve_loopback_tls` tự compose app hiện tại, `src/controlplane/entrypoint.py` chưa có production UI/bootstrap/browser lifecycle.

`loopback_certificate.py` hiện tạo **một** key và certificate tự ký `CN=localhost`, issuer=subject, `BasicConstraints(ca=True)`, SAN `localhost`/`127.0.0.1`, EKU server; **không** có cặp CA/server độc lập. Không dùng `--ignore-certificate-errors-spki-list`, `--certificate-authority` chưa có tài liệu chính thức cho Chromium pin, `ignoreHTTPSErrors`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, HTTP fallback hoặc interstitial bypass.

Thiết kế trust Windows cần proof: launcher cài đúng certificate fixture vào `CurrentUser\Root` cho Chromium qua `certutil -user -addstore Root`; Node process mới phải được spawn với `NODE_EXTRA_CA_CERTS=<certificate.pem>` **trước khi khởi động** để APIRequestContext tin certificate. Hai trust store độc lập: Windows user root không tự bảo đảm Node; `NODE_EXTRA_CA_CERTS` không sửa Windows. Chỉ user store, không elevation hoặc chuyển sang `LocalMachine\Root`. [Chromium Windows trust](https://chromium.googlesource.com/chromium/src/+/main/net/data/ssl/chrome_root_store/faq.md), [Node 22.17 CA env](https://nodejs.org/download/release/v22.17.0/docs/api/cli.html#node_extra_ca_certsfile), [Microsoft certutil](https://learn.microsoft.com/windows-server/administration/windows-commands/certutil). Nếu policy/Chromium pin không chấp nhận self-signed root này: `OPEN/BLOCKED_AUTHORITY`, không đóng bằng bypass; thay PKI cần delta riêng.

Launcher tính thumbprint từ DER và tạo journal run-id ngẫu nhiên, thumbprint, serial, cert file hash, PID **và process creation time của các process workload**; kiểm tra store chưa có thumbprint trước khi cài, chỉ nhận ownership sau add+verify. `finally` đóng Node/browser, dừng listener theo thứ tự an toàn rồi gỡ đúng thumbprint do run sở hữu và verify store; khi lỗi vẫn thử cleanup nhưng không gỡ mù. Stale cleanup chỉ gỡ khi journal/cert/store khớp byte-exact **và** chứng minh mọi process workload của run đã chết bằng PID+creation-time (tránh PID reuse); run còn sống hoặc không xác minh được thì giữ certificate, báo blocker. Không gỡ theo subject hay certificate thuộc run đang hoạt động; journal không chứa private key/capability. Nếu gỡ thất bại, giữ journal để xử lý có kiểm soát.

Contract proof đã được cấp trong CP1 và đã có evidence nêu ở §1, theo thứ tự không gỡ trust của run đang hoạt động: tạo cert, giữ HTTPS listener **còn phục vụ nhưng chưa cài trust**, spawn Chromium mới + Node mới với `NODE_EXTRA_CA_CERTS` bị loại khỏi environment; chỉ nhận negative proof nếu lỗi xác thực certificate, đồng thời probe trusted bằng PEM hoặc TCP xác nhận server vẫn sống (`ECONNREFUSED`/timeout là setup failure). Sau đó cài owned certificate, spawn **client mới** có trust đúng và chứng minh browser navigation + APIRequestContext với `ignoreHTTPSErrors=false`; cuối cùng đóng browser/Node/listener, xác minh toàn bộ workload process của run đã chết rồi mới gỡ certificate/journal/key. Cần quyền thao tác `CurrentUser\Root`, đã được user cấp cho fixture CP1; lượt docs-only này không thực thi lại.

### 2.2. Capability và session không qua kênh công khai để cấp phát

Registry in-memory: launcher issue capability trên **cùng object** đã truyền `create_app`, TTL tối đa 60 giây, workspace/actor cố định ở server-side, redeem một lần. Launcher và Node runner trao đổi riêng qua Windows named pipe cục bộ với tên ngẫu nhiên theo run; chỉ pipe locator và run ID không bí mật được truyền qua environment. Capability, cookie phiên và bootstrap response chỉ được truyền qua IPC/HTTP in-memory; tuyệt đối không đặt trong environment, argv, file, source, metadata, log, trace, video, report hay attachment. Không có public mint endpoint.

Pipe server phải tạo pipe với `FILE_FLAG_FIRST_PIPE_INSTANCE`, DACL chỉ cho SID của user hiện tại và `PIPE_REJECT_REMOTE_CLIENTS`; client xác minh server PID bằng `GetNamedPipeServerProcessId` trước khi gửi. Server lấy client PID từ handle bằng `GetNamedPipeClientProcessId` (không tin PID do client khai), rồi đối chiếu PID **và process creation time** với process tree đã ghi nhận của launcher/Playwright run cùng run binding. Sai owner, PID reuse, process ngoài cây hoặc sai run đều bị từ chối. Framing length-prefix có giới hạn cứng, timeout, một request/redeem, đóng handle khi lỗi và teardown; không kết nối vào pipe không do run sở hữu. Nếu Windows runtime hiện có không cho chứng minh các điều kiện peer/ownership này, prerequisite là `BLOCKED`, ghi exact API/dependency gap và không chạy RED như thể setup đạt.

Delta IPC đã được user duyệt: tối đa **ba lần cấp capability/run**, tương ứng Playwright replacement workers sau expected test failure; mỗi peer PID+creation time chỉ một lần. Mỗi peer mới vẫn qua ownership/process-tree/run-binding verification, capability mới TTL ≤60 giây và single-use; quota ba không thay peer verification.

Collector/reporter: `tests/m2/e2e/fixtures/evidence_reporter.ts` chỉ lưu identity/attempt/status/prerequisite steps/first error đã redaction/file/line/duration bằng atomic write sau mỗi test. HTTP 200 từ response navigation thật; root mount từ assertion đã PASS; không suy từ tên test/stdout/.last-run.json. Setup/hook/TLS/bootstrap/timeout là INVALID_SETUP_FAILURE, giữ partial records; launcher ghi child exit/timeout/cleanup kể cả exception. Proof đã có trong CP1, không rerun nếu không đổi source liên quan.

Bootstrap-only APIRequestContext có CA từ Node env, `ignoreHTTPSErrors=false`, cookie `csrf_token=<nonce>` cho secure origin; POST đúng một `Origin: https://localhost:8000`, `Cookie: csrf_token=<nonce>`, `X-CSRF-Token: <nonce>`, `X-Launch-Capability`. `api/main.py:_valid_origin` và `api/security.py:enforce_csrf` vẫn áp dụng cho bootstrap. Từ `Set-Cookie`, transfer **chỉ** `cp_session` (`HttpOnly; Secure; SameSite=Strict`) và `csrf_token` đã rotate vào BrowserContext in-memory bằng storage state; tạo APIRequestContext dùng tiếp cùng cookie/CA nếu cần API assertion, không ghi auth state ra file. Dispose bootstrap context trước trace/report. Browser API mutation lấy CSRF cookie và gửi header; GET/SSE cần session, không cần CSRF.

Test bootstrap chỉ chứng minh fixture; production launcher cần local trusted capability channel, UI mount, browser/process/trust cleanup khi crash. Exact production delta: `src/controlplane/api/main.py`, `src/controlplane/api/tls.py`, `src/controlplane/entrypoint.py`, mới `src/controlplane/application/local_launch.py`, mới `src/controlplane/infrastructure/security/windows_certificate_trust.py`, mới `tests/m2/test_p8_local_launch.py`. Quyền này khác RED/test fixture; phải có proof launcher thật trước audit đóng P8.

## 4. Contract đã duyệt: state owner, call chain và transaction

**Source xác lập ranh giới, chưa xác lập nghĩa terminal:** `application/control_api/commands.py:start_batch` cùng `infrastructure/db/orchestration/start_batch.py` ghi batch `CREATED`, receipt `current_revision=NULL` và đúng một outbox `production_batch.start_accepted` revision 1; `api/routes/control.py` trả `202`. `docs/09-contracts/01-control-api-and-stream.md` CT-API-001 nói `202` chỉ là ACK và CT-API-007 mô tả operation là trạng thái command bất đồng bộ. `docs/09-contracts/09-orchestration-contracts.md` CT-ORC-001 tách accepted operation khỏi batch; CT-ORC-008/009/010 quy định completion ledger và batch terminal. `domain/statemachine/__init__.py` có graph `OperationState.PREPARED→STARTED→SUCCEEDED` và `BatchState.CREATED→RUNNING→COMPLETED_TARGET`, nhưng validator chỉ kiểm edge/expected revision, không kiểm chứng command đã khởi động hay video đã hoàn tất; `application/projections/operation_view_mapper.py` chỉ map state fact sang `accepted/running/succeeded`. `application/orchestration/__init__.py:CompletionLedgerService.commit` và `infrastructure/db/orchestration/__init__.py:commit_completion` hiện chỉ chèn ledger, không có production caller trọn CT-ORC-008 (job terminal, capacity/variant conversion, MediaUsage, `VideoCompleted`), cũng không có caller production cho `transition_operation`/`transition_batch`. `_operation_row()` trong `control_api_queries.py` luôn trả `accepted`.

**Contract amendment P8-START-001 đã được user duyệt:** operation có `operation_id` của receipt **chỉ theo dõi việc thực thi command `StartProductionBatch`**. `PREPARED/accepted` = đã ghi nhận lệnh và batch `CREATED`; `STARTED/running` = executor tin cậy đã nhận và bắt đầu xử lý command; `SUCCEEDED/succeeded` = trong cùng UoW, application đã chuyển batch `CREATED→RUNNING` với bằng chứng kích hoạt được ràng buộc và command kết thúc. Nó **không** có nghĩa batch `COMPLETED_TARGET`, job `COMPLETED` hay video production hoàn tất. Batch terminal chỉ được công bố theo CT-ORC-008/010: ledger count đạt target cùng các bất biến output/MediaUsage; P8 fixture không tạo ledger giả. So sánh nghĩa SUCCEEDED: tại `202` quá sớm; tại batch terminal trộn command với toàn bộ production và đòi workflow chưa có; tại batch `RUNNING` là lựa chọn hẹp, tương thích `OperationView` và E2E P8. Đây là **amendment đã duyệt**; implementation CP2A có trong worktree nhưng chưa được audit accepted.

Operation source đề xuất `cp_operation_executions(workspace_id UUID, operation_id UUID, receipt_id UUID, batch_id TEXT, state TEXT, revision BIGINT, start_evidence_kind TEXT, start_evidence_ref TEXT, activation_evidence_kind TEXT, activation_evidence_ref TEXT, start_actor_ref TEXT, finish_actor_ref TEXT, created_at, started_at, updated_at, finished_at)` với PK `(workspace_id,operation_id)`, unique `(workspace_id,receipt_id)` và FK composite cùng workspace về receipt/batch. `cp_production_batches.status,revision` là batch source; `cp_video_jobs.status,revision` giữ nguyên job source. Operation rev0 có chủ đích để event đầu của operation dùng rev1, tránh P3 event gap mà vẫn giữ một outbox duy nhất ở P7A; batch `start_accepted` rev1 là event ordering identity đã accepted, batch mới gắn source rev1 khớp từ P8, batch cũ giữ revision `null`/unknown cho tới reconciliation có evidence. P8 consumer `current_revision` đọc applied checkpoint (không lấy source revision vừa ghi); `apply()` so khớp source revision/identity. Fixture driver cung cấp typed evidence chỉ trên DB disposable qua private IPC, application kiểm receipt/batch/revision rồi ghi ref; không ghi SQL trực tiếp, không public endpoint, không dùng test marker để công bố production completion. Production caller và bằng chứng scheduler thật **chưa có source**: fixture success không đóng production completion hay launcher gate.

```text
Browser StartProductionBatch → ControlApiCommandService
  → P1 HTTP UoW: batch CREATED + operation PREPARED + P2 receipt/idempotency + P3 accepted outbox → 202
Private fixture driver → AdminExecutionService.claim_start / confirm_batch_running
  → P1 transition UoW: P4 validator + source CAS + P3 outbox (claim xử lý cả accepted event)
  → cùng transition UoW: P8 event-bound adapter → P3 PostgresEventProcessor
  → P7B PostgresOperationStreamRepository.append (workspace fence → sequence → INSERT)
  → COMMIT nguyên tử → P7B SSE reader/presenter → UI refetch snapshot → AG Grid DOM
```

Callers cụ thể: `api/routes/control.py:start_batch` gọi `ControlApiCommandService.start_batch`; private test driver gọi **hai** method application `claim_start` và `confirm_batch_running` qua port, với browser assertion ở giữa; production executor caller **chưa có source**, không claim real video completion từ test driver. P7A accepted event enqueue ở HTTP UoW nhưng **chỉ process ở UoW claim** để giữ accepted H29/H31 một outbox và không stream sớm; event P8 mới enqueue+process trong chính caller-owned UoW. Rollback của từng UoW xóa đúng các source/outbox/checkpoint/SSE write thuộc UoW đó; không biến HTTP `202` đã commit thành rollback của bước claim sau. Crash trước commit claim/confirm không để partial transition; crash sau commit có source + stream để snapshot/reconnect. Existing `PostgresOutboxPublisher.dispatch` chỉ lookup event_id/mark published và observer list, **không** phải background outbox→projection worker. Adapter đọc applied revision từ `cp_event_checkpoints` của P8 consumer (không từ source vừa ghi), `apply()` xác thực source state/revision/event identity; append và checkpoint thuộc accepted `PostgresEventProcessor`. New event phải trả `applied`; replay chỉ nhận `deduplicated` khi source/checkpoint khớp, còn `out_of_order`/`gap_blocked`/`quarantined` phải raise để rollback UoW, không commit trạng thái hiển thị lệch stream. P7B writer/fence duy nhất là `PostgresOperationStreamRepository.append`; không thêm direct SQL writer, không sửa thân P7B accepted. Replay event_id dedup qua checkpoint; stale/lệch thứ tự bị chặn. Outbox chưa xử lý được claim/replay qua cùng consumer sau crash; async dispatch production nếu cần là authority delta mới, không giả định có sẵn.

Batch event `production_batch.start_accepted` giữ aggregate revision 1 theo P7A; batch mới có source rev1 và `production_batch.started` rev2, không đổi semantics P7A lịch sử. Operation event mới dùng `aggregate_type="operation"`, id=operation_id, revision 1 rồi 2 theo operation source; processor hiện append với `operation_id=None`, nên UI refetch bằng `resource_type/resource_id` chứ không đòi stream row `operation_id` FK. Nếu P7B contract cần giá trị cột này, `OPEN` và xin delta thân processor, không ghi SQL khác. Job event chỉ phát nếu đi qua application transition thật; không giả lập từ job row.

## 6. SSE và snapshot recovery

P7B gửi `id:<cursor>`, `event:<event_kind>`, `data:{...}`; dùng `addEventListener` cho named event, không `onmessage` mặc định. `resync_required` có `action="query_resource_snapshots"` rồi stream đóng. Query `cursor` khác `Last-Event-ID` trả `CURSOR_MISMATCH`; cursor ahead/unknown là HTTP ProblemDetail. **Native `EventSource.onerror` không đưa status/body**: UI không được đọc hoặc tuyên bố thấy `CURSOR_*` từ callback. Contract `CURSOR_*` kiểm bằng APIRequestContext/HTTP test; UI `onerror` chỉ hiển thị degraded/reconnecting, health/snapshot `fetch` có session để phân biệt auth/server failure, backoff. Nếu cần đọc exact stream ProblemDetail trong browser, phải dùng request riêng được abort và không coi đó là body của `onerror`.

Chiến lược duy nhất: initial/reload/resync tạo `EventSource('/v1/operations/stream')` **không query cursor**, đợi open và buffer event, sau đó fetch tất cả **trang nằm trong phạm vi contract** của operations/batches/jobs, dựng snapshot source state/revision, drain buffer theo cursor; event chỉ refetch detail và bỏ qua nếu `event.resource_revision <= cached.revision` (nếu event không có revision hợp lệ thì refetch an toàn). Trong mất mạng ngắn, giữ chính EventSource để browser gửi `Last-Event-ID` tự quản khi reconnect; **không** giữ `?cursor` cũ với header mới. `resync_required` đóng object cũ, bỏ buffer, subscribe no-cursor rồi snapshot lại. Không suy status từ event; nếu snapshot operation/batch chưa có revision hoặc list chưa có, đường này `BLOCKED_AUTHORITY`, không gọi là recovery đã giải quyết. Vì list mới nhất 100 không bao phủ toàn bộ dataset, không claim global exhaustive recovery; detail của resource đang hiển thị được refetch theo id, dataset scale/pagination giữ `OPEN`.
